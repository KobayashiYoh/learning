# Learning

## Chapter 1: Introduction

- ソフトウェア開発における最大の制約は「自分たちが作っているシステムを理解できるかどうか」
- 複雑さへの対処法は「コードを単純・明快にして複雑さを取り除く」と「複雑さをカプセル化する」の2つ
- ウォーターフォールは最初に全体を設計して固定するので設計変更で複雑さが爆発する
- 漸進的開発（アジャイルなど）は小さな機能単位で設計を繰り返すので早い段階で設計の問題を修正できる
- 確かに大規模なプロジェクトほど設計変更が場当たり的で複雑だが、アジャイル開発は変更範囲が小さく設計を変えやすい印象
- 開発者は常に設計、複雑さについて考え続けるべき
- この本では複雑さとは何か学び、複雑さを最小化する技法を紹介してくれる

## Chapter 2: The Nature of Complexity

- 設計がシンプルかどうかを判断する判断力がシンプルな設計を生む力を育む
- 滅多に触らない箇所に複雑さを閉じ込めれば複雑さは取り除ける
- 自分には簡単でも他人が複雑だと感じるならそのコードは複雑（胸に手を当てて考えたい...）
- 一概に複雑さと言っても変更の増幅（単純な変更に多くの修正が必要）、認知不可、未知の未知（どこを変更すべきか何を知るべきかわからないタチが悪いヤツ）がある
- 複雑さの原因は依存関係と不明瞭さの2つ
- 複雑さは1つの致命的な失敗がもたらすのではなく、小さな依存や不明瞭さが何百、何千と積み重なることで生じる
- 今まで悪い設計は大きな1回の失敗によって生じるものだと思っていたので驚いた
- 「今回の変更ぐらいなら」という妥協の積み重ねが複雑さを生んでしまう
- 設計の際に小さな妥協を取り除きたいと思った（少し心当たりがあって胸が痛い...）

## Chapter 3: Working Code Isn't Enough

- 良い設計にはマインドセットが重要
- 戦術的プログラミング...目の前のタスクを最速で動かすことに集中するのでその場しのぎ
- 戦略的プログラミング...長期的な視点で設計を考え、複雑さを最小化することに注力する
- 良い設計者への第一歩は「動くコードだけでは不十分」と認識すること
- 事前の投資...最初の案で決めず複数の設計を検討する（Claude CodeのPlanモードとか使えそう）、将来の変更を想定する、良いドキュメントを書く
- 事後の投資...設計上の誤りを見つけたら、無視したりパッチでしのいだりせず、少し時間をかけて直す
- 小さな投資の目安は開発時間の10〜20%
- 私は逆に小さな投資へ時間を使い過ぎているかもしれないので削るべきかもしれない...
- 劣悪なコードベースは採用にも悪影響
- Facebookは「Move fast and break things」で成功したが、のちにコード品質で苦しんでスローガンを改めた
- 投資は時間を消費するが、長い目で見ると元が取れる

## Chapter 4: Modules Should Be Deep

- 各モジュールをインターフェース（使う側が知るべきこと＝何をするか）と実装（どうやるか）に分けて考える
- 最良のモジュールはインターフェースが実装よりはるかにシンプルなもの
- 明確に定義されたインターフェースは未知の未知を減らす
- モジュールを長方形にたとえると、面積が機能、上辺の長さがインターフェースの複雑さに当たる
- この長方形のエピソードは「ドメイン駆動設計をはじめよう」でも紹介されていた
- シンプルなインターフェースの裏に多くの機能を持つ「深い」モジュールが最良
- インターフェースはコスト、機能は利益
- クラス病...「クラスやメソッドは小さくすべき」「N行を超えたら分割せよ」という通念が行き過ぎた状態
- インターフェースはシンプルに、機能は複雑にという考え方はとても勉強になったので開発でも実践したい

## Chapter 5: Information Hiding (and Leakage)

- 情報隠蔽は深いモジュールを作るための最も重要な技法
- privateで宣言すれば良いというわけではない（getter/setterで露出すると結局publicと一緒）
- たしかにとりあえずprivateで宣言してgetter/setterもとりあえず用意しましたのようなコードはたまに見かける
- 情報漏洩は一つの設計判断が複数のモジュールに反映されている状態
- 情報漏洩の対策は、クラスを統合するか、その知識だけをカプセル化する新しいクラスを作ること
- HTTPのバージョンやDateヘッダなどははライブラリが自動で設定すべき
- クラス内部ではprivateメソッドごとに情報や機能を閉じ込めてインスタンス変数を使う箇所をできるだけ少なくする
- 性能に関わる設定パラメータなどのモジュールの外で必要な情報は隠してはならない

## Chapter 6: General-Purpose Modules are Deeper

- 汎用モジュールは不要な機能になったり、今後の設計に合わなかったりするリスクがある
- 特化型モジュールは漸進的開発と相性が良い
- 筆者の結論は「ある程度汎用的」が最適とのこと
- インターフェースは特定用途に絞らず、一般化する
- 大事なのは再利用性よりもインターフェースがシンプルで深くなること
- インタフェースの最大の目的は再利用性だと思っていたので、衝撃だったが納得した
- 設計の要は誰が、何を、いつ知る必要があるかを見極めること
- 「必要を満たす最もシンプルなインターフェースか？」「幾つの場面で使われるか？」「今の用途で使いやすいか？」を自問自答する
- 汎用的なインターフェースはメソッドが少なく深く、クラス間の分離もきれいになる

## Chapter 7: Different Layer, Different Abstraction

- 良い設計は各層が上下の層とは異なる抽象を提供する（例: ファイルシステムの「ファイル」→「ブロックキャッシュ」→「デバイスドライバ」）
- 不要なパススルーメソッドの根本原因は責任分担の混乱
- パススルーメソッドの対策は(b) 下位クラスを呼び出し側に直接公開する、(c) 機能をクラス間で再配分する、(d) クラスを統合するの3つ
- デコレータは既存オブジェクトを包んでほぼ同じAPIで機能を追加するパターン
- デコレータがパススルーメソッドや浅いクラスを量産する原因に
- クラスのインターフェースと内部表現の違いこそがクラスが提供する価値
- パススルー変数はパススルーメソッドの変数版（いわゆるバケツリレー）
- インターフェース、引数、クラスなど設計要素を1つ追加するたびに、学ぶべきものが増えるので、追加する要素はその学び以上に複雑さを取り除く必要がある

## Chapter 8: Pull Complexity Downwards

- 複雑さを下に押し下げる（ここでいう下はモジュール内部で上は利用者のこと）
- モジュールの複雑さは利用者ではなくモジュール内部で引き受けるべき（なぜなら、利用者は開発者より多いため）
- 設定パラメータは、複雑さを下ではなく上に押し上げる典型例
- パラメータを公開する前に、「利用者（上位モジュール）は、ここで決めるより良い値を決められるか?」と自問する
- デフォルト値を使用し、例外のみ指定するようにする
- 利用者の苦労を減らすために自分が少し余分に苦労する機会を探すべき
- 実装だけでなくスキルの作成などでも役に立ちそうな考え方

## Chapter 9: Better Together Or Better Apart?

- 小さく分けるほど個々は単純になるが、分割自体が複雑さを生む
- コードの短さについて触れられたが、コードが短くなることはそんなに大事なのだろうか？
- インターフェースが単純になるなら統合する（中間のインターフェースが消え、デフォルト化などで機能を自動化できる）
- 長さだけを理由に分割すべきではない
- 大事なのはシグネチャが単純で読みやすいこと
- 分割が有効になるのは(b) 独立したサブタスクを切り出す場合と、(c) 無関係な複数の機能を別メソッドに分ける場合（呼び出し側が単純になるときに限る）の2つ
- 分割するか統合するかの判断軸は情報隠蔽が最も良く、依存が最も少なく、インターフェースが最も深くなる構造を選ぶ

## Chapter 10: Define Errors Out Of Existence

- 最も重要な教訓は、例外を処理しなければならない箇所を減らすこと
- 過度な防衛は不要な例外を増やす
- APIでそもそも例外が起こらないように定義しておく
- 例外は低いレベルで検出、処理して上位に知らせないようにマスキングする
- 多くの例外を1つのハンドラで処理して例外を集約する
- メモリ不足のような処理する価値がないかつまれにしか起きないエラーはいっそのことクラッシュさせてしまう
- 例外を処理せずクラッシュさせるのは斬新でびっくりだが、合理的な判断だと思った
- そもそも例外を定義する機会が今ままであまりなかったので、例外を定義する際に読み返したい

## Chapter 11: Design it Twice

- 2回設計せよ
- 「正直めんどくさそう...」と思ってしまったが、細部まで詰める必要はないとのこと
- 互いに大きく異なる案ほど学びが多い
- 比較は二者択一ではなく、複数の案の良い点を組み合わせてより良い案が生まれることもある
- Claude CodeのPlanモードに設計を2種類考えてもらって実践してみようと思った
- 2回設計は、設計が良くなるだけでなく、何が設計を良くし悪くするのかを学べるため、設計スキルそのものも向上する

## Chapter 12: Why Write Comments? The Four Excuses

- ドキュメントコメントは理解を助けるだけでなく、抽象化に不可欠であり、設計そのものを改善する
- コードを読めばわかることはコメントに書かない→メソッドが細分化される→浅いメソッドが増える
- 複雑さを抽象化で隠すためにコメントは必須
- 今だったらコメント以外にAIに内部実装を呼んで貰うということもできそう
- 筆者の主張も理解できるし、かと言ってコードから理解できる内容のコメントを書くのも保守性を下げると思った

## Chapter 13: Comments Should Describe Things that Aren't Obvious from the Code

- コメントはコードからは明らかでない情報を伝えるために書かれる
- コードとは異なる詳細度（より細かく、またはより抽象的に）で書かれる
- Javadoc、Doxygen、godocなど、ツールの規約に従う
- 原則としてすべてのクラス、メソッド、クラス変数にコメントを書く
- 1行ごとに同じ内容を言い換えたコメントや、名前の単語を並べ直しただけのコメントは無価値
- 抽象化はコメントでしか記述できない
- 複数モジュールにまたがる判断は、開発者が自然に目にする場所に書く
- 「明らか」かどうかは、初めてコードを読む人の視点で判断する（レビュアーが分かりにくいと言ったら、議論せずに改善する）

## Chapter 14: Choosing Names

- 1つの名前の影響は小さくても、変数は何千とあるため、全体では大きな差になる（複雑さは少しずつ増える）
- コードを読む人は名前を信じるので、悪い名前はバグの原因になる
- 「宣言もドキュメントも見ずに名前だけを見て、どこまで正しく推測できるか」と自問自答する
- 抽象的な名称や具体的刷り具命名を避ける
- 正確で直感的な短い名前が思いつかないときは、変数の定義や目的が曖昧な兆候である（1つの変数に複数の意味を持たせているなど）
- 名前が思いつかないのは自身のネーミングセンスだと思っていたが、実は設計に原因があるかもしれないので、今後は命名で迷ったら設計も疑いたい
- 一貫性には、(1) その用途には常に同じ名前を使う、(2) その名前を他の用途に使わない、(3) 同じ名前の変数がすべて同じ振る舞いをするよう、用途を十分に狭くするという3つの条件がある

## Chapter 15: Write The Comments First

- コメントはコードを書く最初の段階で書くのがよい
- TDDみたいだと思った（TDDはテストを実装より先に書き、本章はコメントを実装より先に書く）
- 「コードがまだ変わるから」と後回しにすると、多くの場合そのまま書かれないし、書いたとしてもコードの繰り返しのようなコメントになる
- 設計の要点が頭に新しいうちに記録でき、実装に気を取られずに抽象とインターフェースに集中できる
- 抽象を完全に表現できるのはコメントだけであり、実装前に抽象を見直して調整できるので、設計が良くなる

## Chapter 16: Modifying Existing Code

- 必要最低限のみ既存コードを修正しようとするのは戦術的プログラミング
- 変更のたびに特殊ケースや依存が増え、設計が少しずつ悪化する
- 理想は、変更を終えた時点で、最初からその変更を想定して設計したかのような構造になっていること
- 変更そのものにリファクタリングが不要でも、触った箇所で設計を少しでも改善する
- 「制約の中でできる最善か」を問い、数日で済む代替案を探したり、締め切り後に時間をもらえるよう交渉したりする←やってる人見たことある！
- コメントは説明対象のコードの近くに置くほど更新されやすい
- 設計判断は一度だけ、最も分かりやすい場所に書く、あるいはdesignNotesを使う
- コミット前に数分かけて変更全体を見直し、ドキュメントに反映されているかを確認する←hooksで仕組み化できそう

## Chapter 17: Consistency

- 一貫性は一度学べば他の場所にもその知識を使える「認知的なてこ」となる
- 見た目が似ていれば中身も同じだと安全に推測できるため、ミスも減る
- 一貫性の例として、名前、コーディングスタイル、インターフェース、デザインパターン、普遍条件がある
- コーディングスタイルはLinterなどでカバーできそう
- 一貫性を保つ対策は「文書化する」「強制する」「郷に入っては郷に従え」「既存の制約を変えない」
- 異なるものを無理に同じ方法に押し込むとかえって複雑さと混乱を生む

## Chapter 18: Code Should be Obvious

- 不明瞭さの対策はコードを明白に書くこと
- イベント駆動型プログラミングは、ハンドラは間接的に呼ばれ、どれが呼ばれるかは実行時の登録次第なので、制御の流れを追いにくい
- コードの意味や振る舞いをざっと読んで理解できないなら、読み手にすぐには伝わらない重要な情報がある
- ソフトウェアは、書きやすさよりも読みやすさを優先して設計すべき
- 読み手の期待に反するコードはコメントで補足する
- 抽象化や特殊ケースの除去で、必要な情報の量そのものを減らす

## Chapter 19: Software Trends

- オブジェクト指向のprivateメンバーは情報隠蔽に役立つ
- インターフェス継承は実装が多いほどインターフェースは深くなるので複雑さに対して有効
- 実装継承は親がデフォルト実装を持つのでコードは減るが情報が重複して親子間で状態を共有するため情報漏洩が起こる
- アジャイル開発はこの本の考え方と一致するが、機能優先で戦術的プログラミングにならないよう注意
- 単体テストがないと大きな構造変更を避けるようになって複雑さが蓄積する
- TDDは特定の機能を動かすことを目的としている戦術的プログラミングに近いので筆者は否定的
- ただ、バグ修正においては、先に失敗するテストを書いて本当に治ったかを確認するTDDの思考は有用
- デザインパターンは有用だが、過剰な適用に注意
- インスタンス変数を公開したい場合はゲッターとセッターを使うのは理にかなっているが、そもそも情報隠蔽に反するので公開しない方が良い
- 浅いメソッドでインターフェースを散らかすだけで、Javaでは使われすぎている
- 新しい開発パラダイムに出会ったら、「大規模システムの複雑さを本当に減らすか」という観点で吟味すべき
- 自分も覚えたことはすぐ使いたくなるので気をつけたい

## Chapter 20: Designing for Performance

- きれいな設計を犠牲にせずに高い性能を得るにはシンプルさが重要
- シンプルさは設計を良くするだけでなく、システムも速くする
- 何が高コストかは、マイクロベンチマークで測って学ぶ
- 効率化に複雑さが伴う場合、小さくインターフェースに影響しない隠れた複雑さなら検討の価値がある
- 性能に関する直感は、経験者でも当てにならないのでやはり計測が重要
- まずキャッシュの導入やアルゴリズムの変更など、根本的な改善を探す。それがない場合の最後の手段が、既存コードの再設計
- 複雑なコードは余計な処理をするため遅くなりがちである

## Chapter 21: Conclusion

- この本が扱ったただ一つのテーマが「複雑さ」
- 複雑さへの対処は最も重要な課題
- 複雑さの根本原因は依存関係と不明瞭さ
- 設計はパズルみたいで楽しいというのは共感できた
- あとは実践あるのみだと思った
